# План разработки: Гео-мессенджер

Приложение, в котором сообщение доставляется получателю только когда он физически оказывается в заданной точке.

## 0. Быстрый тестовый MVP (1-2 недели, личный сценарий)

Цель — проверить саму механику "геозона → уведомление" на живых людях, прежде чем вкладываться в полноценную разработку. Все функции ниже — временные упрощения, не финальная архитектура.

**Экраны (4-5 штук)**
1. Логин по номеру телефона
2. Список контактов — можно через "пригласить по ссылке" вместо полноценной системы друзей
3. Создание сообщения: текст + кнопка "поставить на текущей точке" (без карты, без выбора точки вручную)
4. Список полученных сообщений (сработавшие/ещё нет)
5. Push/локальное уведомление при срабатывании

**Что урезано ради скорости**
- Радиус фиксированный (например, 100 м), без настройки пользователем
- Нет выбора точки на карте — всегда текущая геопозиция отправителя
- Нет статусов "доставлено/прочитано" на этом этапе
- Нет групп, вложений, голоса

**Технически проще всего**
- Flutter + Firebase целиком: Firebase Auth, Firestore (вместо PostgreSQL на этом этапе), FCM — для 10-20 тестовых пользователей этого достаточно, не нужен отдельный бэкенд
- Геозоны через пакет `geolocator`

**Метрика успеха**
Если через неделю хотя бы половина тестеров создала больше одного сообщения без напоминаний — механика цепляет, переходим к полноценной разработке (Этапы 1-6 ниже) и решаем, в какую сторону масштабировать: бытовые сценарии, B2B-квесты (см. раздел 8) или что-то, что подскажут сами пользователи.

---

## 1. Цель и MVP-функционал (полноценная версия, после теста)

- Регистрация/авторизация пользователей
- Список контактов (друзья/связи)
- Создание сообщения: текст + геоточка (текущая или выбранная на карте) + радиус срабатывания + получатель
- Доставка сообщения через геозону + локальное/push-уведомление
- История отправленных/полученных сообщений

## 2. Технологический стек

| Слой | Технология |
|---|---|
| Мобильное приложение | Flutter (кроссплатформенно iOS/Android) |
| Геолокация/геозоны | `geolocator`, `flutter_local_notifications`, нативные Geofencing API |
| Бэкенд | Node.js (NestJS/Express) или Python (FastAPI) |
| База данных | PostgreSQL + расширение PostGIS |
| Push-уведомления | Firebase Cloud Messaging (FCM) |
| Аутентификация | Firebase Auth или собственный JWT |
| Хостинг бэкенда | Render / Railway / VPS |

## 3. Архитектура

```
[Клиент A: создаёт сообщение]
        │
        ▼
   [Backend API] ── сохраняет в PostgreSQL/PostGIS
        │
        ▼
[Клиент B: получает список активных геозон для себя]
        │
        ▼
[ОС мониторит вход в геозону через Geofencing API]
        │
        ▼
[Локальное уведомление на устройстве B]
        │
        ▼
[Клиент B открывает сообщение → статус "доставлено" отправляется на сервер]
```

## 4. Схема базы данных (упрощённо)

**users**
- id, name, phone/email, push_token, created_at

**contacts**
- user_id, contact_id, status (accepted/pending)

**messages**
- id, sender_id, recipient_id
- text
- location (geography(Point, 4326)) — через PostGIS
- radius_meters
- status (pending / delivered / read)
- created_at, delivered_at

**geofence_sync** (опционально, для оптимизации лимитов на устройстве)
- user_id, message_id, synced_at

## 5. Этапы разработки

### Этап 1 — Backend (база)
1. Настроить PostgreSQL + PostGIS
2. Спроектировать и создать таблицы (users, contacts, messages)
3. REST API:
   - `POST /auth/register`, `/auth/login`
   - `GET /contacts`, `POST /contacts/add`
   - `POST /messages` — создать гео-сообщение
   - `GET /messages/nearby?lat=&lng=` — получить активные геозоны для пользователя (через PostGIS `ST_DWithin`)
   - `PATCH /messages/:id/delivered`

### Этап 2 — Мобильный клиент: базовый UI
1. Экраны: логин/регистрация, список контактов, создание сообщения (с картой для выбора точки), список входящих/исходящих сообщений
2. Интеграция карты (Google Maps SDK / Mapbox)
3. Подключение к API

### Этап 3 — Геозоны и уведомления
1. Запрос разрешений на геолокацию (foreground + background)
2. При получении нового сообщения — регистрация геозоны через `Geolocator`/нативный Geofencing API
3. Обработка события входа в зону → показ локального уведомления
4. Ограничение количества активных геозон (iOS: 20, Android: ~100) — синхронизация только ближайших N точек, обновление при значительном перемещении пользователя (Significant Location Change)

### Этап 4 — Push-уведомления (резервный канал)
1. Настройка FCM
2. Отправка push, если приложение закрыто и локальная геозона не сработала (резерв через периодическую серверную проверку)

### Этап 5 — Доработки
1. Статусы сообщений (доставлено/прочитано) с отображением у отправителя
2. Возможность отмены/редактирования ещё не доставленного сообщения
3. Приватность: скрытие точки на карте от отправителя после отправки, ограничение точности радиуса
4. Оптимизация батареи (снижение частоты опроса геолокации)

### Этап 6 — Тестирование и релиз
1. Тестирование геозон на реальных устройствах (эмуляторы плохо симулируют GPS-события)
2. Нагрузочное тестирование PostGIS-запросов
3. Публикация в App Store / Google Play

## 6. Риски и нюансы

- **Лимиты геозон** — решается синхронизацией только релевантного подмножества точек
- **Разрешения на фоновую геолокацию** — iOS/Android всё жёстче ограничивают это, нужно объяснять пользователю зачем это нужно (UX-онбординг)
- **Расход батареи** — предпочтение нативным Geofencing API вместо постоянного опроса координат
- **Приватность** — избегать хранения истории перемещений без необходимости

## 7. Возможное расширение (после MVP)

- Групповые гео-сообщения
- Голосовые/медиа-сообщения
- Публичные гео-метки (открытые всем в радиусе)
- Web-версия для просмотра истории

## 8. B2B-направление (если личный сценарий подтвердится и захочется масштаба)

Не удаляем из бэклога — держим как вариант роста после теста на друзьях.

**Сценарии**
- Городские квесты/экскурсии — цепочка гео-сообщений (подсказка → следующая точка → финал)
- Ивенты — свадьбы, фестивали, корпоративы
- Ритейл/HoReCa — гео-промо рядом с точкой бизнеса (строго opt-in)
- Музеи/выставки — гид-контент у экспонатов

**Изменения в продукте**
- Роль `organization` в таблице users, с отдельными правами
- Таблица `campaigns` — группа сообщений/точек, объединённых квестом/ивентом
- Веб-дашборд (React) для создания кампаний
- Аналитика: события входа в зону, открытия сообщения, времени у точки

**Монетизация**
- Подписка для организаций по числу активных кампаний/точек
- Разовая оплата за постановку ивента/квеста под ключ
- White-label для музеев/турагентств
- Комиссия с продажи билетов на квесты, если платформа берёт на себя продажу участия

## 9. Другие идеи монетизации/направлений на будущее

- **Бытовые напоминания** — "напомни купить хлеб, когда буду у магазина". Ближе всего к личному сценарию, может стать отдельным лёгким tier продукта (не сообщение другу, а самому себе)
- **Гео-дневник/капсула времени** — сообщение самому себе в будущем, привязанное к месту (открывается через месяц/год, когда снова окажешься там). Хорошо продаётся как эмоциональный/ностальгический продукт, монетизация — подписка за расширенное хранилище
- **Партнёрская программа с картами/навигаторами** — интеграция с Google Maps/2ГИС как "гео-заметки" через API, доход от партнёрства вместо прямой монетизации пользователей
- **Геймификация для розницы через B2C, а не B2B продажу** — не бизнес платит за размещение, а пользователи сами создают публичные метки ("здесь вкусный кофе"), а бизнес получает аналитику по подписке — сначала растим пользовательскую базу органически, монетизируем позже
- **API/SDK для разработчиков** — продавать саму геозон-инфраструктуру (доставка сообщений по локации) как сервис другим приложениям, если механика окажется технически сильной и надёжной
